## 1. 概要（What & Why）

### アプリの名前

・プロ野球選手検索・比較アプリ
・阪神タイガースと広島東洋カープの選手を対象としたRAGアプリ。

### 解決したい問題

・プロ野球選手について調べる際、選手ごとに情報を検索する必要がある。
・2025年の成績を確認したり、複数選手の成績を比較したりする場合、必要な情報を自分で集める手間がかかる。
・「阪神の投手」や「広島の野手」のように、チームやポジションを条件に選手を探す場合も、複数の情報を確認する必要がある。
・そこで、選手情報をあらかじめデータベースに登録し、質問に応じて必要な情報を検索・回答できるアプリを作成した。

###　なぜベクトルDB × LLMを選んだのか

・ベクトルDB（ChromaDB）
　・選手データを登録し、ユーザーの質問に関連する情報を検索するために使用する。
　・質問に関連する選手情報を取得することで、LLMが回答するときの根拠となる情報を用意できる。

・LLM（OpenRouter）
　・ベクトルDBから取得した情報をもとに、ユーザーが理解しやすい自然な文章で回答するために使用する。
　・複数選手の情報をまとめて比較するなど、単純な検索結果の表示だけでは難しい処理にも対応できる。

・ベクトルDBとLLMを組み合わせる理由
　・ベクトルDBで必要な情報を検索する。
　・検索した情報をLLMに渡して回答を生成する。
　・ベクトルDBだけでは検索結果の表示が中心になるが、LLMと組み合わせることで、検索した情報をもとに自然な文章で回答できる。
　・LLMだけに回答させるのではなく、登録した選手データを検索してから回答させることで、データを根拠とした回答を生成できる。
　・この仕組みにより、ベクトルDBとLLMを組み合わせたRAGシステムを実現した。



## 2. 使い方（How to run）

### 環境構築手順

・Pythonがインストールされている環境で実行する。

・プロジェクトフォルダへ移動する。

cd C:\Users\01231013\Desktop\iti23\baseball-rag-app


・仮想環境を作成する。

python -m venv .venv


・仮想環境を有効化する。

```powershell
.\.venv\Scripts\Activate.ps1
```

・必要なライブラリをインストールする。


pip install -r requirements.txt


### APIキーの設定

・OpenRouterを使用するため、OpenRouterのAPIキーが必要。

・APIキーはOpenRouterの公式サイトから取得する。

・取得したAPIキーをプロジェクト直下の`.env`に設定する。


OPENROUTER_API_KEY=自分のAPIキー


・APIキーはソースコードに直接記述せず、`.env`で管理する。

.envは.gitignoreに登録し、GitHubなどへ公開しない。

### データの登録

・プロジェクトフォルダで以下のコマンドを実行する。
python ingest.py

・dataフォルダ内の選手データを読み込む。

・データをチャンクに分割し、Embeddingを生成する。

・生成したEmbeddingと選手情報をChromaDBへ登録する。

### アプリの起動

・以下のコマンドでStreamlitを起動する。
streamlit run app.py


・起動後、ブラウザで表示されたURLを開く。

・画面上の入力欄からプロ野球選手について質問する。

### 質問例

・「佐藤輝明について教えて」

・「佐藤輝明の2025年成績を教えて」

・「阪神の投手について教えて」

・「広島の野手について教えて」

・「佐藤輝明と小園海斗の2025年成績を比較して」

## 3. 設計判断（Design decisions）

### 埋め込みモデルの選定理由

・埋め込みモデルにはopenai/text-embedding-3-smallを使用した。
・OpenRouter経由で利用でき、選手情報の検索に必要な文章の意味的な類似性を扱えるため採用した。
・データ登録時とユーザーの質問を検索するときの両方で、同じ埋め込みモデルを使用している。

### チャンク戦略

・選手ごとのMarkdownデータを、400文字を目安としてチャンクに分割した。
・チャンク間には80文字の重複を設定した。
・1つのチャンクを大きくしすぎると、検索時に不要な情報まで取得される可能性があるため、選手情報をある程度まとまった単位で検索できるサイズにした。
・チャンク間を80文字重複させることで、文章がチャンクの境界で分断された場合でも関連する情報を取得しやすくした。

### データ件数と選定理由

・阪神タイガースと広島東洋カープの2チームを対象とした。
・19選手分のデータを作成し、チャンク分割によって27チャンクをChromaDBに登録した。
・投手と野手の両方を含めることで、チームやポジションを指定した検索に対応できるようにした。
・複数選手のデータを登録することで、選手同士の成績比較にも対応できるようにした。
・RAGの検索と回答処理を確認しやすい規模として19選手を選定した。


### データ形式

・選手1人につき1つのMarkdown（.md）ファイルとしてデータを作成した。
・Markdownファイルには、選手名、所属チーム、ポジション、基本情報、2025年の成績、選手の特徴などを記載している。
・dataフォルダに保存したMarkdownファイルを読み込み、400文字を目安にチャンクへ分割している。
・チャンク分割したデータからEmbeddingを生成し、選手情報と合わせてChromaDBへ登録している。

### LLMモデル選定

・LLMにはnvidia/nemotron-3-super-120b-a12b:freeを使用した。
・OpenRouter経由で利用でき、検索した選手情報をもとに自然な文章を生成できるため採用した。
・選手の特徴や2025年の成績を回答したり、複数選手の成績を比較したりできる点を重視した。
・APIキーやモデル名などの設定は`.env`で管理し、ソースコードに直接記述しない構成とした。

### 良かった点

・選手名を指定した質問では、対象の選手情報を検索して正しく回答できた。
・「阪神の投手」や「広島の野手」のように、チームとポジションを指定した検索にも対応できた。
・複数の選手名を指定することで、選手同士の成績比較にも対応できた。
・ChromaDBから検索した情報をLLMに渡すことで、検索結果をそのまま表示するのではなく、自然な文章で回答できた。
・UIとRAGの処理を分離したことで、検索や回答生成の処理を整理して実装できた。

### 改善したい点

・現在は阪神タイガースと広島東洋カープの2チームが中心なので、今後は他球団の選手データも追加したい。
・登録する選手数を増やすことで、より多くの選手を検索・比較できるようにしたい。
・現在はチームやポジションの条件をプログラム側で判定しているため、より多様な質問にも対応できる検索方法に改善したい。
・選手データの更新を簡単にできるようにし、最新の成績を反映できる仕組みにしたい。
・検索結果が多くなった場合でも、必要な情報を優先して回答できるように検索精度を改善したい。
